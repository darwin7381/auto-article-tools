# Console 設計文件 — 為什麼舊版 40 分、現版 20 分、80 分要長什麼樣

## 1. 使用者與工作（Jobs-to-be-Done）

BD 編輯每天的真實工作迴圈：

1. 收到一篇業務稿（docx/pdf/Google Docs/微信文/Medium…，简繁英混雜）
2. 丟進系統 → 等 AI 處理（2~3 分鐘）→ **這段時間他會切去做別的事**
3. 回來看結果 → 校稿（改錯字、調語氣、刪贅句）→ 確認上稿參數
4. 發到 WordPress → 把連結交差
5. 不滿意某一段 AI 處理 → 只重跑那一段，不要整條重來

關鍵洞察：**步驟 2 的「切走再回來」是常態**。任何「刷新就丟狀態」的設計都直接違背真實使用。

## 2. 舊版憑什麼有 40 分（優點，必須全數保留並超越）

| # | 優點 | 為什麼有效 |
|---|---|---|
| O1 | 拖放上傳 + 檔案卡 | 最低摩擦的進稿 |
| O2 | 連結類型自動偵測徽章 | 使用者不用懂技術差異 |
| O3 | 文稿類型→押註→供稿方一條龍 | 把編輯室規則固化成表單 |
| O4 | 逐階段進度 + 狀態訊息 + 查看 | 等待過程有掌控感 |
| O5 | 整體進度條（含動畫） | 一眼知道進行到哪 |
| O6 | TipTap 可視化/HTML 雙模式校稿 | 編輯的核心工具 |
| O7 | 完整 WordPress 表單（含自動提取提示） | 上稿參數透明可改 |
| O8 | 自動/手動模式 | 信任時全自動，不信任時逐步把關 |

## 3. 舊版為什麼只有 40 分（天花板，80 分要打破的）

| # | 缺陷 | 證據 |
|---|---|---|
| X1 | **刷新即死**：整條狀態在 React state，離開頁面=全丟 | ProcessingContext 無任何持久化 |
| X2 | **不能重跑中間步驟**：錯了只能整條重來 | 無 resumeFromStage |
| X3 | **零可觀測**：不知道每步花多久、用什麼模型、改了什麼 | ProgressDisplay 無 elapsed/model |
| X4 | **看不出 AI 改了什麼**：content_ai → pr_writer 之間的變化是黑箱 | 只有單頁查看 |
| X5 | 一次只能跑一篇；歷史紀錄近乎沒有 | 無 job 概念 |
| X6 | alert() 式回饋、錯誤訊息含糊 | 多處 alert |
| X7 | 1632 行單檔元件，改一處全頁重渲染 | IntegratedFileProcessor |

## 4. 我的 20 分版差在哪（誠實自評）

複刻了 O1-O8 的「形」，但：結果埋在 JSON 卡片裡（內容不是主角）、刷新一樣丟視圖（X1 沒解）、有 job 系統但 UI 當它不存在（單次性思維）、alert() 還在（X6 沒解）、零耗時/模型/差異可觀測（X3/X4 沒解）。**= 把舊版搬家，沒有進化。**

## 6. 不做什麼（與為什麼）

- 不做使用者系統/權限（內部工具，過早）
- 不做 prompt 版本歷史（等 eval 體系一起做才有意義）
- 不抄舊版 4-tab 分頁切換：單頁漸進式（進稿→進度→成品→上稿）少一層心智負擔，配合 B2 執行列取代「切 tab 找東西」

## 7. 實作要點

- 後端：runner 每階段記 `elapsed_ms` 進 stage done 事件（持久化既有機制自動帶）
- 前端拆檔：`toast.tsx`（通知）、`diff.ts`（行級 LCS）、`Stages.tsx`（卡片 v2：耗時/模型/字數/diff）、`RunsStrip`（執行列）、`App.tsx`（attach 機制：create 與 reattach 共用同一條輪詢+SSE 路徑）
